# 나만의 프롬프트 관리 프로그램

자주 사용하는 AI 프롬프트를 등록하고, 카테고리별/키워드로 찾아보고, 즐겨찾기로 관리할 수 있는 터미널 기반 프로그램입니다.

## 실행 방법

```bash
python3 main.py
```

실행 후 메뉴에 표시되는 번호(0~7)를 입력해 원하는 기능을 사용합니다.

## 카테고리

텍스트 생성, 이미지 생성, 영상 생성, 페르소나, 자동화, 기타, 직접 입력 중에서 선택할 수 있습니다.

## 자료구조 설계

프롬프트 데이터는 **딕셔너리를 원소로 갖는 리스트**(`prompts = [{"title": ..., "content": ..., "category": ..., "favorite": ...}, ...]`)로 관리합니다.

- **리스트를 선택한 이유**: 메뉴에서 번호(인덱스)로 프롬프트를 선택하는 방식이라 등록 순서를 그대로 유지할 수 있어야 하고, 목록 전체를 순회하며 필터링/검색하는 연산이 잦기 때문입니다.
  - 장점: 등록 순서 보장, 인덱스로 즉시 접근 가능, `for`문으로 필터링·검색 구현이 단순함
  - 단점: 특정 제목을 바로 찾으려면 처음부터 끝까지 순회(O(n))해야 하며, 데이터가 아주 많아지면 검색 성능이 떨어짐
- **딕셔너리를 선택한 이유**: 프롬프트 하나가 제목/내용/카테고리/즐겨찾기 여부라는 여러 속성을 가지므로, 필드 이름으로 값을 다루면 코드 가독성이 좋아지기 때문입니다.
  - 장점: `prompt["title"]`처럼 필드명으로 접근해 의미가 명확함, 필드 추가·삭제가 자유로움
  - 단점: 필드명 오타 시 즉시 오류가 나지 않고 `KeyError`로 나타남, 클래스/`dataclass`와 달리 필드 구성이 강제되지 않아 항목마다 구조가 어긋날 위험이 있음

## 프로그램 흐름 설계

`main()`은 `while True`로 메뉴를 반복 출력하고 사용자 입력을 받습니다. 몇 번 반복할지 미리 알 수 없는 대화형 프로그램이라 조건식으로 반복 횟수를 제한하기보다, 사용자가 종료를 원할 때(`0` 입력) `break`로 명시적으로 루프를 빠져나가는 방식을 선택했습니다. 이렇게 하면 종료 시점이 코드가 아니라 사용자의 선택에 달려 있다는 의도가 분명해집니다.

## 검색 구현 방식

`search_prompts`는 정규식이나 형태소 분석 없이, `in` 연산자로 제목/내용에 검색어가 **부분 문자열로 포함되는지**만 검사하고 `.lower()`로 대소문자를 구분하지 않습니다.

- 선택 이유: 완전 일치보다 사용성이 좋으면서도 추가 라이브러리 없이 가장 간단하게 구현할 수 있습니다.
- 한계: 오타나 유사어(동의어)는 찾지 못하고 정확한 문자열 포함 여부만 확인합니다. 또한 매 검색마다 전체 리스트를 순회(O(n))하므로 데이터가 많아지면 느려질 수 있습니다.

## 데이터 영속화 (설계 제안)

현재는 프로그램을 종료하면 메모리에 있던 프롬프트 데이터가 모두 사라집니다(파일 저장 없음). 추후 영속화를 추가한다면 **JSON 파일(`prompts.json`)** 저장을 제안합니다.

- 이유: 현재 자료구조(리스트+딕셔너리)와 JSON 구조가 1:1로 대응되어 `json.dump`/`json.load`만으로 변환이 가능하고, 사람이 파일을 열어 직접 확인·수정하기도 쉽습니다.
- 대안과 비교: CSV는 표 형태라 리스트 안에 중첩된 딕셔너리 구조를 표현하기 까다롭고 `favorite`의 불리언 타입 정보도 문자열로 손실됩니다. SQLite 같은 DB는 단일 사용자용 로컬 CLI 프로그램 규모에 비해 과한 선택이라고 판단했습니다.

## 동명/중복 처리 정책

- **제목 중복**: 현재 구현은 제목이 같아도 검증 없이 그대로 등록을 허용합니다. 프롬프트는 번호(인덱스)로 구분하므로 제목이 겹쳐도 기능상 문제가 없기 때문입니다.
- **카테고리 충돌**: "직접 입력"으로 기존 카테고리(예: "텍스트 생성")와 동일한 문자열을 입력하면 별도 병합 처리 없이 같은 문자열이므로 `view_by_category`의 `set()` 집계에서 자동으로 같은 카테고리로 합쳐집니다. 다만 공백이나 대소문자가 다르면(`"텍스트 생성 "` 등) 다른 카테고리로 분리되어 나타납니다.
- **향후 정책 제안**: 제목 중복은 경고만 띄우고 등록은 계속 허용(사용자의 의도를 존중), 카테고리 직접 입력 시에는 앞뒤 공백을 `strip()`하고 기존 카테고리 목록과 비교해 같은 이름이면 그대로 합치도록 개선할 수 있습니다.

## 함수 구조

기능 단위로 함수를 분리해 각 함수가 하나의 책임만 갖도록 구성했습니다. 이렇게 나누면 특정 기능을 수정할 때 다른 기능에 영향을 주지 않고, 코드를 읽을 때 `main()`의 메뉴 분기만 봐도 전체 흐름을 파악할 수 있습니다.

| 함수 | 역할 | 분리 이유 |
| --- | --- | --- |
| `create_default_prompts` | 초기 샘플 프롬프트 데이터 생성 | 데이터 초기화 로직을 프로그램 실행 로직(`main`)과 분리해, 샘플 데이터를 바꾸더라도 다른 코드를 건드리지 않도록 함 |
| `add_prompt` | 제목/내용/카테고리를 입력받아 새 프롬프트 등록 | 입력값 검증(빈 값 방지)과 등록 로직을 하나의 기능 단위로 묶음 |
| `list_prompts` | 전체 프롬프트 목록을 즐겨찾기 표시와 함께 출력 | 조회 로직을 재사용할 수 있도록 별도 함수로 분리 |
| `view_by_category` | 카테고리를 선택해 해당 카테고리 프롬프트만 출력 | 목록 조회(`list_prompts`)와 다른 필터링 로직이라 별도 함수로 분리 |
| `search_prompts` | 키워드로 제목/내용을 검색 | 검색이라는 독립된 기능이라 조회·필터링 함수와 분리 |
| `show_prompt_detail` | 번호를 선택해 프롬프트 상세 내용 출력 | 목록에는 없는 상세 정보(내용 전체) 출력을 별도로 처리 |
| `manage_favorites` | 번호를 선택해 즐겨찾기 설정/해제 | 데이터를 변경하는 로직이라 단순 조회 함수들과 분리 |
| `show_favorites` | 즐겨찾기로 지정된 프롬프트만 출력 | 즐겨찾기 조회를 별도 기능으로 노출 |
| `show_menu` | 메뉴 화면 출력 | 화면 출력(UI)과 메뉴 선택 처리(`main`)를 분리해, 메뉴 문구만 바꿀 때 로직을 건드리지 않도록 함 |
| `main` | 메뉴 반복 출력 및 사용자 입력에 따라 각 기능 함수 호출 | 전체 프로그램의 흐름 제어만 담당하고, 실제 기능 구현은 각 함수에 위임 |

## 커밋 정책

기능 단위로 커밋을 나눕니다. 하나의 커밋에는 하나의 기능 추가/수정만 담아, 나중에 특정 기능이 언제 어떻게 추가됐는지 히스토리에서 바로 찾을 수 있도록 합니다. 커밋 메시지는 `유형: 내용` 형식을 사용합니다.

| 유형 | 의미 | 예시 |
| --- | --- | --- |
| `add:` | 새 기능 추가 | `add: 프롬프트 검색 기능 구현` |
| `clean:` | 디버그 코드 제거 등 정리 | `clean: 목록 기능 완성 후 임시 디버그 출력 제거` |
| `docs:` | 문서 변경 | `docs: README에 프로젝트 소개 및 사용법 작성` |
| `merge:` | 브랜치 병합 | `merge: 프롬프트 목록 기능 브랜치 병합` |

## 브랜치 전략 및 병합 이력

기능 단위로 브랜치를 만들어 작업한 뒤 완성되면 `main`에 병합합니다. 예를 들어 프롬프트 목록 기능은 별도 브랜치에서 작업(`c9531a3`)했고, 동작을 확인한 뒤 `main`에 병합(`d867f0b`)했습니다.

- **분리 기준**: 기능 단위(예: 목록 조회, 검색, 즐겨찾기 등)로 브랜치를 나눕니다.
- **병합 기준**: 해당 기능이 정상 동작하는 것을 확인한 뒤에만 `main`으로 병합합니다.
- **이유**: `main` 브랜치는 항상 실행 가능한 상태로 유지하고, 기능별 작업 이력을 분리해두면 문제가 생겼을 때 어느 기능에서 발생했는지 추적하기 쉽습니다.
